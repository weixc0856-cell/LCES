# LCES 项目完整改进方案
## 从一次性生成内容，升级为可追溯、可验证、可持续迭代的课程工程系统

**文档性质：** 产品、架构、模型路由、内容质量与实施路线统一方案  
**项目：** Local Content Engineering Studio（LCES）  
**版本：** 1.0 — 综合设计建议  
**决策原则：** 复用已有治理能力，优先修复真实生产瓶颈；所有关键结论以代码、测试和运行证据为准。

---

# 一、执行摘要

## 1.1 项目目前真正的问题是什么

根据本轮提供的代码审计，LCES 并不是缺乏工程架构，也不是缺乏全部质量门禁。当前已经存在：

- Gate 1–4、内部与公共内容类型边界；
- 证据台账、主张与来源关联、引文逐字核验；
- Renderer Registry、审批、发布白名单；
- 浏览器 QA、结构化内容契约；
- 固定模板与 JSON 数据驱动的图形和动画能力。

这些机制是项目的基础资产，应当保留。

目前最严重的问题，是**内容生产能力落后于工程治理能力**。

一次论文课程试跑中，最终产生的演示版、阅读版和口播内容只有三章，单个章节内容浅，多个版本相互重复。演示版仍然是纵向滚动的文章页面，没有真正的幻灯片浏览体验，也没有足够的公式、图表、算例与动画。

从已提供的代码审计来看，问题可以归纳为六个层面：

1. **输入不完整**：研究阶段只读取论文开头的一部分，导致实验结果、消融研究、表格和复杂度讨论未进入模型上下文。
2. **生成预算没有接线**：`Settings.max_output_tokens` 没有实际传递到生成请求；请求默认输出上限为 4096 token。
3. **模型路由能力不足**：研究、规划、章节生成和审核没有根据任务复杂度、上下文需求与成本充分分工。
4. **内容生产缺少覆盖与深度约束**：大纲和章节生成缺少强制覆盖矩阵、单元级深度要求和可恢复的生成状态。
5. **内容质量门禁不足**：结构合法、引用存在，不代表课程讲得完整、公式解释正确、实验分析充分。
6. **展示层不匹配课程形态**：现有模板将章节渲染成纵向文章，没有独立的展示页面模型、翻页交互和逐页质量验收。

此外，还存在配置与代码漂移、输出截断信息丢失、缺失图片静默删除、生成运行记录不完整等问题。

## 1.2 项目应当达到的目标

LCES 应从“模型生成几份 HTML 和 JSON 文件”升级为：

> 用户提供论文或技术资料，系统通过可追溯研究、覆盖规划、教学单元生成、证据校验、质量审核和受控渲染，生产一套内容完整、教学清晰、视觉专业、可以恢复和复现的课程资产。

最终交付不应只有一个 HTML 文件，而应包含：

- 可核验的研究与证据记录；
- 可校验的课程蓝图和覆盖矩阵；
- 统一的课程主数据；
- 可独立生成、审核和重跑的教学单元；
- 派生的演示版、阅读版和讲者备注；
- 16:9 演示页面与可复用的视觉资产；
- 质量报告、模型调用记录和审批记录；
- 经过验证的发布产物。

## 1.3 总体实施顺序

| 优先级 | 阶段 | 主要目标 |
|---|---|---|
| P0-A | 审计归档与契约冻结 | 定义课程应当覆盖什么、如何追溯 |
| P0-B1 | Provider 与模型路由 | 接通输出预算、截断检测、云端 API 和成本治理 |
| P0-B2 | 分节研究与覆盖规划 | 消除头部截断，建立论文地图与覆盖矩阵 |
| P0-B3 | 单元级生成与审核 | 逐单元生成、校验、修订和恢复 |
| P1 | 演示界面 | 16:9、翻页、目录、进度、全屏、打印 |
| P2 | 视觉与动画 | 公式、图表、架构图、必要的程序化动画 |
| P3 | 生产化与商业验证 | 可复现运行、成本优化、稳定发布、用户反馈 |

以上阶段不是按日期机械推进。每个阶段都必须通过明确的验收条件，才能进入下一阶段。

# 二、产品定位与设计原则

## 2.1 产品定位

LCES 是一个 local-first、model-agnostic、evidence-traceable 的内容工程系统。

它不是简单的 AI 写作工具，也不是通用幻灯片编辑器，更不是依靠单个模型一次性完成研究、写作、设计和发布的系统。

它的核心价值在于：

1. 将复杂资料转换为结构化、可追溯的知识资产；
2. 将长任务拆解成可验证、可恢复的子任务；
3. 根据任务需求选择合适的本地或云端模型；
4. 通过程序化规则与人工审核共同保证质量；
5. 将统一内容资产转换成不同交付形式；
6. 将生成过程、审核结果和发布记录纳入工程治理。

## 2.2 六项不可妥协的原则

### 原则一：证据优先于表达

任何关键事实、实验结果、公式和定量结论都必须能追溯到原始资料。表达可以润色，但不能为了叙事完整而补造事实。

### 原则二：内容深度优先于页面数量

课程不是把一段文字拆成更多页。每个教学单元必须完成明确的教学任务。

### 原则三：模型生成与确定性工程分离

模型负责理解、推理、组织与表达。程序负责契约验证、文件处理、哈希、状态管理、渲染、权限边界和可重复检查。

### 原则四：一个内容真源，多个确定性产物

演示版、阅读版和讲者备注不能继续作为三份互相独立的正文分别生成。

### 原则五：失败必须显式化

截断、缺证据、缺图片、依赖不匹配、预算超限、API 故障和 QA 失败都必须产生明确状态，不允许静默降级。

### 原则六：视觉确定性不能凌驾于证据确定性

漂亮的页面、顺畅的动画和自动化测试通过，都不能证明内容本身正确。

# 三、目标系统架构

## 3.1 总体架构

```text
用户资料 / 论文 / 技术文档
             |
             v
      Ingestion & Source Map
             |
             v
      Sectioned Research
             |
             v
 PaperMap + Evidence Ledger
             |
             v
      Coverage Planning
             |
             v
 Outline + LearningUnit Plan
             |
             v
     Unit Generation Queue
             |
             v
     Unit Validation & Review
             |
             v
         CourseMaster
             |
       +-----+------+
       |            |
       v            v
 PublicContent   Internal Assets
       |            |
       v            v
 Slide Deck     Presenter Notes
 Reading Edition Visual Assets
       |
       v
 Browser QA + Release Gates
       |
       v
 Approved Release Artifacts
```

模型路由器与 Provider 层贯穿研究、规划、生成和审核阶段。文件存储、状态机、证据治理和发布控制由 LCES 自身负责。

## 3.2 系统责任边界

| 模块 | 应承担的责任 | 不应承担的责任 |
|---|---|---|
| Ingestion | 提取文本、保留章节与页码、计算来源哈希 | 自行补全缺失资料 |
| Research | 提取主张、证据、实验和局限 | 将推测包装成已证实事实 |
| Coverage Planning | 检查论文要素是否得到教学安排 | 只按模型偏好决定讲什么 |
| Model Router | 选择模型、预算、重试和降级策略 | 无条件在模型失败时切换到低能力模型 |
| Unit Generator | 生成独立、可审核的教学单元 | 一次性承担整篇课程的全部生成任务 |
| Validation | 验证结构、证据、深度和覆盖 | 把模型自评当成真实验证 |
| Renderer Registry | 将公共内容渲染为受控交付形式 | 允许模型直接执行任意 HTML、JS 或系统命令 |
| Release | 执行审批、白名单和发布限制 | 发布未审核的内部内容 |

**架构决策：** 继续使用现有的模型、内容类型、渲染器注册表、门禁和审批机制。新功能应扩展现有接口，不得形成平行的内容系统。

# 四、内容契约与统一内容真源

## 4.1 新增或完善的核心数据实体

以下是目标数据模型。实施前需要与仓库已有的 Pydantic 模型、schema 和数据库结构对齐，避免重复定义。

### A. PaperMap

论文结构地图，记录：

- 原始章节和子章节；
- 关键公式；
- 图和表；
- 实验任务与实验设置；
- 主要结果；
- 模型变体与消融；
- 复杂度讨论；
- 作者明确说明的局限；
- 关键结论及其证据位置。

每个要素需要具备稳定 ID、来源 locator、必需性和验证状态。

建议的状态包括：

- `verified`
- `unverified`
- `not_found`
- `not_applicable`
- `needs_review`

不能因为模型没有找到某项内容，就默认该项不重要。

### B. CoverageMatrix

将 PaperMap 中的论文要素映射到教学单元。

每项至少记录：

- `paper_item_id`
- `required`
- `covered_by`
- `coverage_status`
- `evidence_ids`
- `review_status`

关键论文要素没有对应教学单元时，课程不能通过完整性门禁。

### C. LearningUnit

教学单元是内容生产和审核的最小核心单位，不是幻灯片。

每个单元应当具有：

- 稳定的 `unit_id`；
- 教学目标；
- 前置知识；
- 关键概念；
- 正文 blocks；
- 公式、算例或推导；
- 证据与主张引用；
- 视觉需求；
- 讲者备注；
- 质量状态；
- 预计讲解时间；
- 输入版本与生成记录。

一个复杂公式可以分为多个教学单元；一个简单结论也可能只需要一个单元。

### D. CourseMaster

课程的唯一内部主数据，汇总：

- 课程元信息；
- 章节和单元顺序；
- 单元正文；
- 教学目标；
- 证据关联；
- 视觉资产引用；
- 讲者备注；
- 覆盖矩阵；
- 审核状态。

### E. UnitDraft 与 UnitRun

每个教学单元的生成过程应当有独立记录。

建议状态机：

```text
planned
   |
   v
generating
   |
   v
generated
   |
   v
validating
   |
   +----> needs_revision
   |             |
   |             v
   |          generating
   |
   +----> blocked
   |
   v
approved
```

并提供 `retryable_failure`、`cancelled` 等终止或恢复状态。

已经 `approved` 的单元默认不可覆盖。需要修改时，应创建新版本或执行明确的 reset 操作。

## 4.2 主数据派生规则

目标派生关系：

```text
CourseMaster
    |
    +----> PublicContent
    |          |
    |          +----> Slide Deck
    |          +----> Reading Edition
    |
    +----> Internal Presenter Notes
    |
    +----> Evidence & QA Report
```

演示版和阅读版可以采用不同的布局与表达密度，但事实内容、公式、数据和证据引用必须来自同一份经过审核的主数据。

讲者备注和内部审核信息必须保持在内部通道中，不得进入公共 HTML。

对于阅读版，引用可以展示页码、章节或表格编号等 locator；内部系统则继续保存完整的 claim、evidence 和 source 关联。

# 五、研究阶段：从头部截断改为分节研究

## 5.1 现状问题

根据本轮代码审计：

- 研究阶段的文本预算约为 20,000–24,000 字符；
- 截断逻辑保留输入开头；
- 下游还有 30,000 和 12,000 字符的头部截断；
- PDF 页文本拼接后，部分页边界丢失；
- 研究模型没有完整的论文结构地图。

对于一篇包含实验表格、消融研究、公式和复杂度分析的论文，这会系统性地遗漏关键内容。

因此，不能通过单纯提高字符上限来解决问题。

## 5.2 目标研究流程

### 第一步：程序化分节

先根据原始文档结构切分：

- Abstract；
- Introduction；
- Related Work；
- Method；
- Experiments；
- Results；
- Ablation；
- Complexity；
- Limitations；
- Conclusion；
- References。

实际论文没有对应章节时，保留原始结构，不强行创建。

### 第二步：逐节提取

每个章节分别提取：

- 主张；
- 原文证据；
- 公式；
- 表格和图；
- 实验设置；
- 指标与数值；
- 对照组；
- 作者解释；
- 限制条件。

### 第三步：合并与去重

程序合并分节结果，保留来源 locator、原始文本片段和来源哈希。

合并时可以消除重复记录，但不能删除互相矛盾的结果。冲突应当进入人工审核或明确的 `needs_review` 状态。

### 第四步：构建 PaperMap

最终生成完整的论文结构地图，并对每项内容记录覆盖与证据状态。

## 5.3 来源地图与证据定位

PDF 页面、章节和表格需要稳定定位。

建议建立 `source_map.json` 或等价的数据结构，保存：

- source ID；
- 文件哈希；
- 文档页码；
- 章节路径；
- 原始段落或文本块 ID；
- 表格与图的 locator；
- 解析器版本。

对于扫描 PDF、公式识别失败或表格抽取不可靠的场景，必须显式记录解析限制，而不是把不完整的提取结果当成完整原文。

**验收标准：** 关键论文要素要么有可核验来源，要么明确标记缺失或待审核。不得通过静默截断制造虚假的完整性。

# 六、模型、API 与路由系统

## 6.1 目标：本地优先，但不迷信本地模型

目前本地模型的有效上下文约为 32K。这个约束需要进入路由器和预算器，而不是仅仅写在文档里。

同时要区分三个概念：

1. 上下文窗口决定单次请求能容纳多少输入、输出和其他开销；
2. 输出 token 上限决定单次请求最多可以生成多少内容；
3. 模型能力、推理资源和推理配置影响内容质量、生成速度和稳定性。

这三个因素需要分别测量。

本地模型可以承担简单的分类、格式转换、结构校验辅助和低复杂度章节草稿，但不能默认承担所有复杂研究任务。

云端模型也不是所有任务的默认执行者。它应当用于确实需要更强推理、长材料理解或更高质量生成的环节。

## 6.2 Provider 层的目标能力

扩展现有 Provider 接口，至少支持以下信息：

- `provider_id`
- `model_id`
- `context_window`
- `max_output_tokens`
- `supports_json_mode`
- `supports_json_schema`
- `supports_streaming`
- `supports_cancellation`
- `privacy_class`
- `availability_status`
- `pricing_profile`
- `capability_verified_at`

具体字段应与现有代码契约合并，不要求照搬以上命名。

Provider 响应需要保留：

- 原始或规范化的 `finish_reason`；
- 输入与输出 token 用量；
- 实际模型 ID；
- 响应耗时；
- 错误类别；
- 供应商返回的请求 ID（若有）；
- 可用时的实际费用。

`finish_reason=length` 应映射为明确的截断错误。截断产物不得被标记为通过。

## 6.3 路由策略

| 任务 | 默认策略 | 升级或回退条件 |
|---|---|---|
| 文档解析 | 本地程序 | 解析失败时切换解析策略或请求人工处理 |
| Research | 通过验证的云端模型或分节本地模型 | 证据遗漏、复杂度过高时升级 |
| Coverage Plan | 强规划模型 | 覆盖矩阵不完整时修订 |
| Outline | 强规划模型 | 教学目标或课程范围不合格时重规划 |
| Unit Generate | 按单元复杂度选择 | 公式推导、复杂实验等任务可升级 |
| Unit Review | 独立审核策略 | 关键事实、逻辑或证据不通过时修订 |
| Assemble | 本地程序 | 契约错误时停止组装 |
| Render | 本地受控工具 | 环境或输出错误时显式失败 |
| Final Review | 云端审核与确定性检查组合 | 高风险项目进入人工审核 |

路由策略必须考虑输入长度、预计输出、复杂度、结构化响应能力、历史通过率、隐私限制和费用预算。

## 6.4 输出预算与上下文预算

`Settings.max_output_tokens` 必须接入实际生成调用链。

但是，不能将所有请求统一设置为 65536 token。

建议：

- Research：按章节生成结构化证据记录；
- Coverage Plan：使用紧凑的覆盖关系和缺口列表；
- Outline：生成完整课程结构与单元规划；
- Unit Generate：根据单元复杂度分配输出预算；
- Unit Review：输出问题和修订建议，不重复生成整章。

本地 32K 模型的预算初值可以从输入约 18K–22K token、输出约 2K–4K token 开始验证，但这只是试验起点，必须为系统提示、模板、结构化输出和其他开销留出余量。

预算器必须检查实际 tokenizer 和模型限制，保证请求的输入、输出及相关开销不超过有效上下文。

## 6.5 云端 API 候选与选型方法

建议首轮只接入一个主云端供应商，并保留一个可选的备用 Provider。

可评估的候选包括：

- DeepSeek API；
- 阿里云 Model Studio / Qwen API；
- OpenAI API；
- 后续根据实际需求补充其他供应商。

具体模型 ID、上下文长度、输出上限、结构化输出支持、价格、地区可用性和数据条款都需要在接入时从官方文档重新核验，并通过真实请求测试。

不应在代码中假设：

- 某家服务一定能从当前账户和地区访问；
- 兼容 OpenAI API 就意味着所有参数完全兼容；
- 支持 JSON Mode 就一定支持严格 JSON Schema；
- 上下文很长就一定更适合每次输入整篇论文。

### 云端 Provider 准入条件

1. 官方接口和当前模型规格可以核验；
2. 账户、支付和网络可用性通过实际测试；
3. 鉴权、限流、超时和错误处理可用；
4. 能记录实际模型、token、耗时和请求 ID；
5. 数据处理条款和隐私要求经过审核；
6. 费用预算和调用上限可以执行；
7. 失败时不会静默切换到不满足能力要求的本地模型。

## 6.6 隐私、成本和可靠性

每个任务都应当有：

- 最大调用次数；
- 最大重试次数；
- 任务级费用上限；
- 单元级预算；
- 可恢复的状态；
- 供应商级熔断；
- 明确的降级策略。

错误处理至少区分：

- 鉴权失败；
- 余额不足；
- 限流；
- 网络错误；
- 超时；
- 上下文超限；
- 输出截断；
- 结构化输出失败；
- 内容质量不通过。

只有临时性错误才适合自动重试。鉴权失败不能反复请求；截断应该优先调整输出预算或拆分单元；内容质量不通过则需要修订或升级模型。

本地专属材料不得因为云端失败而自动上传。API Key 不得进入仓库、提示词、生成产物或普通日志。

# 七、课程规划与单元级生成

## 7.1 不再让模型一次性决定整门课程

课程生成应拆成：

```text
PaperMap
   |
   v
CoverageMatrix
   |
   v
Course Outline
   |
   v
LearningUnit Plan
   |
   v
Unit Generation
   |
   v
Unit Validation
   |
   v
Course Assembly
```

大纲阶段应明确：

- 课程目标；
- 目标受众；
- 前置知识；
- 必须覆盖的论文要素；
- 章节之间的依赖关系；
- 每个单元的教学目标；
- 所需公式、算例、图表和实验分析；
- 预计讲解时间；
- 需要人工审核的风险点。

课程蓝图应先经过结构和覆盖校验，再进入生成阶段。

## 7.2 教学单元的深度要求

每个单元的内容深度应根据类型判定，不能用统一的字数阈值。

例如：

| 单元类型 | 必须完成的教学任务 |
|---|---|
| 概念解释 | 定义、动机、工作机制、边界条件 |
| 公式推导 | 变量定义、公式来源、推导步骤、适用条件 |
| 算法流程 | 输入、处理步骤、输出、复杂度或限制 |
| 实验分析 | 实验目标、设置、指标、结果、解释与限制 |
| 对比分析 | 对比维度、证据、适用范围、不能直接比较的因素 |
| 工程应用 | 使用场景、实现路径、约束、失败模式 |

对关键概念，通常应至少包含解释和推导、公式演算或具体算例中的一种；对于论文实验单元，则必须深入解释实验设置、结果和结论边界。

不应要求每一页都放公式或算例。深度标准应由单元类型决定。

## 7.3 单元级重试与恢复

提供类似以下的操作能力：

```text
lces run --from-stage unit_generate --unit unit-007
```

该操作只表示目标设计，实际 CLI 参数需与当前命令体系对齐。

应当支持：

- 只重跑失败单元；
- 保留已审核单元；
- 查看生成与审核历史；
- 比较不同版本；
- 显式 reset；
- 重新组装整门课程；
- 重新运行指定质量检查。

这会显著降低长课程的重复调用成本。

## 7.4 三种交付形式的派生

演示版、阅读版和讲者备注不再分别独立生成。

- **演示版**：围绕一个核心观点、一张图或一个推理步骤组织内容。
- **阅读版**：提供更完整的解释、证据定位、公式推导和参考文献。
- **讲者备注**：补充讲解顺序、口头说明、提问与转场内容，严格保持内部隔离。

三种形式可以拥有不同的表达密度，但必须来自同一份审核通过的 CourseMaster。

# 八、内容质量门禁与证据治理

## 8.1 现有机制应当继续使用

不重建现有 Gate 1–4、内部/公共类型边界、审批、白名单和证据治理。

真正需要补充的是内容质量检查，以及让配置文件真正成为执行依据。

## 8.2 建议新增的关键检查

| Check ID | 目标 | 建议策略 |
|---|---|---|
| `coverage_matrix_complete` | 必需论文要素全部有教学单元归属 | 阻断 |
| `claim_linkage` | 关键主张关联到证据与教学单元 | 阻断 |
| `evidence_quotes_in_source` | 关键引文可在来源中核验 | 阻断 |
| `truncation_free` | 没有接受截断的生成产物 | 阻断 |
| `unit_depth` | 单元完成其对应教学任务 | 阻断或人工审核 |
| `unit_duplication` | 检查单元间重复与空洞拆分 | 超阈值时审核 |
| `formula_verified` | 关键公式与推导得到核验 | 人工或专门验证器 |
| `visual_semantics_reviewed` | 图形表达没有改变技术含义 | 关键图形人工审核 |
| `duration_within_tolerance` | 实际课程时长符合计划范围 | 试验阶段观察，验证后再设阻断 |
| `release_boundary_valid` | 公共产物不含内部备注和敏感信息 | 阻断 |

`unit_duplication` 不能只依靠文本相似度。两个单元可能文字不同但观点相同，也可能共享公式却承担不同教学任务。因此应当结合重复检测、单元职责和人工审核。

## 8.3 配置与代码必须统一

当前审计指出，`config/quality_gates.yaml` 没有被代码读取，实际 blocking/advisory 行为由代码默认值控制。

应当：

1. 让配置文件真正进入校验执行链；
2. 为每个检查定义唯一 `check_id`；
3. 明确严重等级与阻断策略；
4. 对未知检查项和缺失配置显式报错；
5. 生成可追溯的 QA 报告；
6. 为关键配置添加测试，防止未来漂移。

不能继续让文档、配置和实际行为三套规则并存。

## 8.4 时长不应单独决定质量

当前时长偏差只产生警告，且短课程可能仍然通过后续流程。

应当区分：

- 内容覆盖不完整；
- 单元内容过浅；
- 实际讲解速度差异；
- 讲者备注与正文时长差异。

时长可以作为质量指标，但不应替代内容深度判断。

建议先在完整课程样板中测量实际讲解时间，再决定容差。不能未经实测就将一个固定偏差值变成所有课程的硬性阻断标准。

# 九、演示页面：从文章模板升级为真正的课程界面

## 9.1 页面目标

演示页面采用克制的橙白商务咨询风格：

- 白色或暖白背景；
- 深灰正文；
- 橙色强调；
- 清晰的标题层级；
- 严谨的数据与图表；
- 避免装饰性元素压过内容。

不使用任何未经授权的品牌标识。风格参考专业咨询报告的视觉秩序，而不是复制某个公司的商标或专属设计。

## 9.2 演示版与阅读版分离

阅读版可以继续使用纵向排版，方便搜索、复制、打印和阅读。

演示版应采用独立的 `deck.html.j2` 模板，但仍然只消费现有 `PublicContent` 或其受控派生类型。

建议功能：

1. 固定比例的 16:9 页面；
2. 上一页、下一页；
3. 键盘左右键翻页；
4. 触控与移动端操作；
5. 当前页码和总页数；
6. 进度指示；
7. 目录与章节跳转；
8. 全屏模式；
9. 打印与 PDF 输出；
10. 深色或高对比度辅助模式（可选）。

固定 16:9 不等于所有内容必须挤进一张页面。长公式、复杂表格和推导应当拆分为合理的展示步骤，而不是缩小字号。

## 9.3 页面布局规则

建议建立可复用的布局类型：

- `title`：标题、课程信息与学习目标；
- `key_message`：一个主要结论和必要证据；
- `concept`：概念、解释与示意图；
- `formula`：公式、变量、推导步骤；
- `process`：算法或工程流程；
- `comparison`：对比矩阵；
- `experiment`：实验设计与结果；
- `chart`：数据可视化；
- `case_study`：案例分析；
- `summary`：总结、局限与后续问题；
- `references`：引用与来源。

这些是展示层布局，不应与 LearningUnit 一一绑定。一个教学单元可以派生出多张展示页面。

## 9.4 逐页浏览器 QA

现有浏览器 QA 应当扩展到每张页面，而不是只检查整份 HTML。

建议检查：

- 页面尺寸与比例；
- 横向和纵向溢出；
- 字号与可读性；
- 公式和表格边界；
- 翻页操作；
- 目录跳转；
- 进度更新；
- 全屏行为；
- 键盘和触控可访问性；
- 公共页面没有讲者备注；
- 打印输出正常。

页面布局和交互应由自动化测试验证；信息层次、图表表达和教学节奏仍需要人工审查。

# 十、图形、公式与程序化动画

## 10.1 不要先把所有动画工具接入系统

动画应当用于解释静态页面难以清楚呈现的变化过程，而不是为了让页面显得高级。

优先级建议：

1. 静态 SVG、公式与图表；
2. Mermaid / Graphviz 等已有图形后端；
3. 基于受控模板的步骤动画；
4. 在确有需要时使用 Motion Canvas；
5. 更复杂的视频生产后端另行评估。

现有 Renderer Registry 应当继续作为统一入口。

## 10.2 工具选型原则

- **Mermaid / Graphviz**：流程、架构、依赖和关系图。
- **SVG / 程序化图表**：公式示意、数据图表、局部结构。
- **Motion Canvas**：适合需要时间轴、逐步出现、动态变换的技术教学场景。
- **FFmpeg**：媒体编码与封装。
- **Playwright**：浏览器行为与视觉检查。

Docling、Marp、Slidev、Manim、Remotion 等成熟工具可以作为后续候选，但应通过统一内容契约、质量门禁、许可证和维护成本评估后再决定是否接入。

对于静态演示页面，现有 Jinja 模板可以满足主要需求。没有必要仅仅为了得到 16:9 翻页效果而引入另一套 Markdown 内容源。

## 10.3 Motion Canvas 的特殊约束

根据前述 P0 验收记录，Motion Canvas 当前为 Linux / WSL2 范围内的条件准入方案，不能直接视为已具备跨平台生产能力。

应继续执行：

- Linux 平台准入检查；
- 精确版本校验；
- 渲染期间离线运行；
- 固定依赖与 lockfile；
- JSON 场景契约；
- Python 侧受控子进程调度；
- 帧数、Manifest、编码和媒体 QA；
- 取消、超时和失败状态隔离。

Windows 原生暂不作为 P1 支持平台。若本地 WSL2 环境尚未满足精确 Node 版本要求，应由环境维护者完成准备；LCES 只做版本检查，不自动安装或修改系统。

动画后端不得直接进入正式发布路径，除非其自身的契约、输出与失败处理测试已经通过。

# 十一、运行记录、可复现性与可观测性

每一次研究、规划、生成、审核和渲染，都应当能够回答：

- 这是什么任务？
- 使用了哪些来源？
- 输入发生过哪些变化？
- 使用了哪个模型和提示词版本？
- 产生了哪些输出？
- 是否截断？
- 使用了多少 token？
- 耗时和费用是多少？
- 哪些质量门禁通过或失败？
- 哪些人批准了发布？

建议完善 `generation_trace.json` 或等价的运行记录，至少包含：

- `task_id`
- `run_id`
- `unit_id`
- `stage`
- `provider_id`
- `model_id`
- `prompt_version`
- `input_hash`
- `source_hashes`
- `schema_version`
- `started_at`
- `completed_at`
- `finish_reason`
- `input_tokens`
- `output_tokens`
- `retry_count`
- `error_code`
- `qa_result`
- `build_id`

模型输出不应当被当作唯一审计记录。系统必须保留足够的输入摘要、版本与结果元数据，以便复现问题，同时避免在普通日志中泄漏密钥或敏感原文。

还应修正模型记录不一致的问题。例如运行记录、试跑文档和产物元数据必须指向同一实际模型与运行 ID。

# 十三、《Attention Is All You Need》样板课程试验

样板课程不应再采用三页概述的方式证明系统能运行。它应当用于验证从研究到发布的完整生产链。

## 13.1 先冻结研究范围

课程至少需要覆盖：

1. 论文问题背景与研究动机；
2. 原始 Transformer 整体架构；
3. Scaled Dot-Product Attention；
4. Multi-Head Attention；
5. Positional Encoding；
6. Encoder 与 Decoder；
7. Masking 与自回归生成；
8. 训练目标与优化设置；
9. WMT 2014 实验设计与评价指标；
10. Table 2/3 等关键实验结果；
11. 模型变体、消融与复杂度；
12. 论文贡献、局限与后续影响。

这是一份建议的最低课程范围，不意味着所有主题都只能占一个单元。复杂内容可以拆分，原论文未覆盖的内容必须明确标注为外部补充，不能冒充论文原始结论。

## 13.2 先测试三个代表性单元

在生成整门课程之前，先完成三个有代表性的单元：

- 公式与数值算例：Scaled Dot-Product Attention；
- 结构与机制：Multi-Head Attention；
- 实验解读：WMT 2014 与关键结果表。

每个单元都要通过证据、深度和结构检查，再评估后续生成。

## 13.3 对照试验

| 试验组 | 配置 | 要回答的问题 |
|---|---|---|
| A | 当前本地模型与原流程 | 当前基线质量与成本是多少 |
| B | 本地模型 + 修复输入截断与输出预算 | 工程问题占了多大比例 |
| C | 云端模型 + 同一课程契约 | 云端能力带来多少质量提升 |
| D | 云端研究与复杂生成 + 本地确定性处理 | 混合路由是否更经济、更稳定 |

每组记录：

- 关键要素覆盖率；
- 证据可追溯率；
- 单元完整度；
- 关键事实与公式错误；
- 截断率；
- 重复率；
- 生成耗时；
- token 用量；
- 实际成本；
- 人工审核时间；
- 通过课程门禁的比例。

**最终优化目标不是 token 最少，也不是输出最多，而是单位成本能够稳定交付多少经过审核、可追溯的有效教学内容。**

# 十四、商业与运营视角

LCES 的商业价值不应该建立在“能够生成 HTML”这一能力上，因为通用模型和现成演示工具都可以生成页面。

更有价值的差异化能力是：

- 长材料的结构化研究；
- 可追溯的技术内容；
- 复杂知识的课程化组织；
- 单元级质量控制；
- 可复现的生成流程；
- 本地与云端模型的成本优化；
- 面向专业领域的可靠交付。

初期建议采用低成本验证策略：

1. 先完成一门完整的公开论文课程；
2. 发布研究、课程与视觉资产的质量说明；
3. 让目标用户评价内容深度、可读性和实际用途；
4. 观察用户更愿意为课程内容、专业解读、定制化生成还是生产工具付费；
5. 再决定是否开发面向其他用户的完整产品。

不要先投入大量资源做通用工作台、复杂动画编辑器或多供应商管理平台。它们可以成为后续能力，但目前还不是证明产品价值的最短路径。

# 十五、项目风险清单

| 风险 | 影响 | 控制措施 |
|---|---|---|
| 模型输出质量不稳定 | 内容浅、错误或重复 | 单元级生成、审核与重试 |
| 输入截断 | 关键证据遗漏 | 分节研究、来源地图和覆盖矩阵 |
| 云端费用不可控 | 长课程成本过高 | 预算上限、调用记录、断点恢复 |
| 云端服务不可用 | 任务无法完成 | 明确失败策略、备用 Provider |
| 隐私和数据合规风险 | 材料被不当外传 | 隐私分类、明确的云端准入条件 |
| 配置与代码漂移 | 门禁行为与文档不一致 | 配置实际接线与回归测试 |
| 多版本内容冲突 | 课程事实不一致 | CourseMaster 单一真源 |
| 页面质量掩盖内容问题 | 视觉好但教学差 | 内容质量门禁先于视觉发布 |
| 动画工具集成成本过高 | 项目范围失控 | 只按需集成，逐后端准入 |
| 运行记录不足 | 问题无法复现 | 完整 run trace 与版本元数据 |
| 自动质量指标失真 | 错误地放行或拒绝内容 | 自动化与人工审核组合 |

## 最终结论

LCES 现在最需要的不是再增加一套工具，也不是把本地模型的输出上限调大之后重新生成一次，而是将现有工程治理能力与真正可持续的内容生产能力连接起来。

最重要的四个变化是：

- 从一次性研究改为分节、可追溯的研究；
- 从一次性长输出改为单元级生成；
- 从阶段固定模型改为基于能力、预算与隐私的路由；
- 从结构通过就放行改为覆盖、深度、证据和交付质量共同决定是否通过。

完成这四项之后，再建设演示界面、图形与动画，才能让 LCES 从“能够运行的生成项目”逐步成为“能够稳定交付高质量专业内容的工程系统”。
