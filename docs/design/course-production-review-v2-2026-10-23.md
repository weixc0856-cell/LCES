## 二、下一步 P0-B2.1：真实模型研究试跑

本轮目标不是生成课程，而是回答一个问题：

当前本地模型在完整论文、分节输入和可追踪证据约束下，能否稳定产出足够可靠的研究资产？

### 第一步：确认实际运行的模型

你此前固定的本地模型是 `Qwen3-Coder-30B-A3B-Instruct-Q4_K_M.gguf`，使用本地 `llama-server`。真实试跑前，先按你现有的运行流程确认服务和模型身份，避免把其他模型的结果混进验收。

1. 启动 `start_server.bat`。
2. 检查 `/health` 返回正常。
3. 运行 `lces models`，确认目标模型确实已加载。
4. 运行项目已有的 `--test` 检查。
5. 检查 `/v1/models`，确保服务暴露的模型与本次预期一致。

如果模型身份不匹配、服务未加载或检查失败，停止试跑，不要用其他模型自动替代后继续。

### 第二步：只运行研究阶段

```
lces run --only research
```

这一轮不生成大纲、不生成幻灯片、不生成讲稿，也不执行发布。

运行前后记录：

- 实际 provider 和 model。
- 总区块数、实际处理区块数、失败区块数。
- 每个研究窗口对应的 `chunk_ids`、章节与页码。
- 每次请求的 `finish_reason`、usage、`request_id`、耗时。
- 最终 claim、evidence 的数量。
- 重复主张合并数、无效引用证据丢弃数。
- 超时、JSON 解析失败、截断、重试及最终失败情况。

特别注意：60 个区块不一定等于 60 次请求。 当前实现会先按字符预算打包窗口，所以验收应核对“所有区块是否恰好进入一次预期的研究窗口”，而不是要求调用次数必须等于 60。

### 第三步：建立研究结果的人工抽查表

不要只看 `research_analysis.json` 中有多少条 claim。数量增长不等于研究质量提高。

建议建立一份内部验收表，至少包含以下字段：

| 字段            | 要回答的问题                  |
| ------------- | ----------------------- |
| `claim_id`    | 主张是否有稳定、唯一的内部标识？        |
| 原文定位          | 能否定位到原论文的章节、页码或表格？      |
| 原文依据          | 原文是否真的支持该主张？            |
| `evidence_id` | 证据是否真实存在，且引用的 claim 正确？ |
| 关键数值          | 指标、单位、模型变体、实验条件是否准确？    |
| 主张类型          | 是论文事实、作者解释，还是系统推断？      |
| 完整性           | 是否漏掉必要条件、限定语或反例？        |
| 处理结论          | 保留、修正、合并、拒绝或待核验？        |

对 `Attention Is All You Need`，至少抽查以下内容：

- §3.2.1、§3.2.2、§3.5 等核心机制。
- §5.1–5.4 的训练与实验设置。
- §6.1–6.3 的结果与分析。
- §7 的结论和局限。
- Table 1、Table 2、Table 3 所在区域。
- 关键公式、模型配置、实验比较和重要数值。

对于表格，不能只检查模型是否提取了某个数值，还要核实它对应的模型变体、数据集、评价指标和比较条件。例如，论文中的实验结果应区分 Transformer Base 与 Big 等配置，不能把某个变体的指标无条件泛化为整个模型的统一表现。

### 第四步：评估四种错误，而不只是统计数量

A. 漏提（Omission）

原文存在重要公式、实验结果、限制条件，但研究结果没有对应主张或证据。

B. 误提（Misrepresentation）

模型把原文意思说错，混淆实验条件、夸大结论，或把推断写成论文事实。

C. 证据断链（Broken Linkage）

claim 存在，但 evidence 引用错误、来源定位不准确，或证据并不能支持主张。

D. 重复与过度合并（Duplication / Over-merging）

同一主张被重复保留，或原本条件不同、含义不同的主张被错误合并。

验收报告应分别记录这四类错误。不要用“总共生成了多少条 claim”替代质量判断。

### 第五步：本轮通过条件

以下是建议采用的初始验收标准，不是声称项目当前已经满足的结果。

| 检查项      | 初始标准                      |
| -------- | ------------------------- |
| 区块处理完整性  | 所有预期区块都有明确处理状态，不静默遗漏      |
| 研究请求可追踪性 | 每个窗口可追溯到输入区块、模型、请求与输出状态   |
| 结构有效性    | 研究输出符合契约，ID 与引用关系有效       |
| 关键论文要素   | 核心公式、关键实验、主要结果和局限均有人工核验记录 |
| 关键事实准确性  | 不允许未解决的重大数值、条件或结论错误       |
| 证据链      | 关键 claim 均能回到原文定位并由原文支持   |
| 截断与失败    | 不允许把截断或失败输出静默当成完整研究结果    |
| 重复合并     | 关键主张没有已知的错误合并问题           |

如果真实研究结果中仍存在关键论文要素漏提或明显误述，应先修正研究提取和证据治理，再进入课程单元设计。

## 三、基于真实结果，进入 P0-B3：把课程规划变成可执行的生产流水线

P0-B3 的核心不是简单增加 `unit_generate`，而是建立一套能够按教学单元独立生成、验证、修改、组装，并且不会破坏已验收内容的生产机制。

### 1. 先明确核心数据关系

建议冻结以下数据链路：

SourceMap + ResearchAnalysis

原文区块、主张、证据、页码与章节定位

PaperMap + CoverageMatrix

论文要素、必需项、覆盖状态与缺口

CourseMaster

课程目标、章节、教学单元、顺序与依赖关系

UnitDraft × N

独立生成、局部验证、局部修改与版本管理

组装 → 全局校验 → 人工审批 → 发布

课程、阅读版、讲稿从统一主数据派生

其中，`PaperMap` 负责回答“论文有哪些值得教的内容”，`CoverageMatrix` 负责回答“这些内容是否安排进课程”，`CourseMaster` 负责回答“课程如何组织”，`UnitDraft` 则负责承载每个单元的实际教学内容。

四者不能相互替代。

### 2. 不要把“教学单元”直接等同于“幻灯片”

这是 P0-B3 最重要的产品设计决策之一。

- 一个核心概念可以需要多个教学单元来讲解。
- 一个教学单元可以生成多页幻灯片。
- 一个公式可以先解释物理含义，再推导，最后用案例验证。
- 一个实验结果可以需要实验条件、对比数据和结果解释三页内容。
- 论文中的图表可以被引用，但不能仅仅因为图表已被引用，就认定其结论已被讲明白。

建议采用如下结构：

```
CourseMaster
├── Chapter 01
│   ├── Unit 001: 问题背景与研究动机
│   ├── Unit 002: 既有方法的局限
│   └── Unit 003: 论文的核心贡献
├── Chapter 02
│   ├── Unit 004: 核心机制
│   ├── Unit 005: 公式推导
│   └── Unit 006: 机制与计算成本
└── ...
```

这只是结构示例，不是要求 Transformer 论文必须按这几个单元划分。

真正的单元划分应由论文要素、学习目标、内容复杂度和前置知识共同决定，而不是由模型一次调用时恰好生成了几章决定。

### 3. CourseMaster 必须先于批量单元生成

不要直接把 CoverageMatrix 交给模型，让它自由生成整门课。

建议先通过确定性规则建立课程规划草案，再让模型辅助组织和解释：

1. 收集所有必需论文要素。
2. 按研究问题、理论机制、数学推导、实验方法、结果、局限等类别分组。
3. 标记教学依赖关系，例如先理解注意力机制，再解释多头注意力。
4. 为每个单元指定学习目标和必需论文要素。
5. 为每个单元指定证据引用与必要的公式、图表、例子。
6. 检查所有必需项是否分配，是否存在循环依赖或明显重复。
7. 经过规划校验后，冻结本轮 `CourseMaster`，再开始单元生成。

关键原则：覆盖矩阵决定必须讲什么，课程规划决定按什么顺序讲，模型负责把内容讲清楚。

模型可以提出课程结构修改，但不能静默删除必需论文要素。

## 四、P0-B3 的工程实现要求

### 1. 单元任务队列与局部重试

建议为每个教学单元建立独立任务状态，例如：

`planned → generating → generated → validating → approved`

异常状态至少包括：

- `retryable_failure`：超时、暂时性服务错误等。
- `needs_revision`：内容质量不符合要求，需要修改。
- `blocked`：缺少必要证据、依赖或审批。
- `cancelled`：任务被明确取消。

命令接口可以按现有 CLI 设计扩展，例如：

```
lces run --from-stage generate --unit unit-007
```

这是建议的目标接口，实际实现前应与现有 CLI 契约对齐。

必须满足：

- 重跑一个单元不会重新生成整门课程。
- 已批准单元默认不可被覆盖。
- 单元重试必须保留之前的运行记录。
- 失败的单元不能静默从课程中消失。
- 如果课程规划或论文地图发生变化，系统应能识别受影响的单元并要求重新验证。
- 组装阶段必须检查单元版本与当前课程规划版本是否一致。

### 2. 从一个主数据源派生三种产物

建议让 `CourseMaster` 和经审核的 `UnitDraft` 成为内容真源，而不是分别调用模型生成三份完整文档。

| 产物        | 推荐生成方式                |
| --------- | --------------------- |
| 公开课程 HTML | 从审核通过的课程内容生成，不暴露内部 ID |
| 阅读版       | 从同一课程内容及证据定位确定性生成     |
| 演讲稿       | 基于单元内容生成，保留讲解节奏与过渡语   |

这能减少三份内容之间的事实矛盾、重复段落和篇幅失衡。

内部数据仍然保留 `claim_ids`、`evidence_ids`、来源定位及审核状态。公开层只呈现读者需要的引用、脚注或来源信息，不暴露内部追踪标识。

### 3. 单元质量门禁

建议先实施以下门禁，再逐步调整阈值。

| 门禁                          | 通过要求                  | 失败处理       |
| --------------------------- | --------------------- | ---------- |
| `coverage_matrix_complete`  | 必需论文要素均有有效单元覆盖        | 阻断         |
| `unit_depth`                | 核心概念具备解释、推导或示例等必要教学内容 | 阻断         |
| `claim_linkage`             | 关键事实能追溯至有效主张与证据       | 阻断         |
| `truncation_free`           | 不接受被截断却被当作完整结果的产物     | 阻断         |
| `evidence_quotes_in_source` | 关键引用与原文一致             | 阻断         |
| `unit_duplication`          | 不存在未经解释的明显重复          | 超阈值后阻断或待复核 |
| `duration_within_tolerance` | 实际课程时长符合明确的目标时长       | 校准后阻断      |
| `formula_verified`          | 数学推导与公式含义已完成必要核验      | 未核验不得标记已审核 |
| `visual_semantics_reviewed` | 图表含义、标注与数据表达经过检查      | 未核验不得标记已审核 |

注意，`unit_depth` 不应对所有单元使用完全相同的规则。背景单元、公式推导单元和实验分析单元，需要不同的验收条件。

相似度阈值也应通过真实课程样本校准。不要一开始就把某个相似度数值当成普遍有效的学术标准。

### 4. 修复门禁配置与实际执行的偏差

你此前的审计发现 `quality_gates.yaml` 尚未真正被代码消费。如果这一点仍然存在，应把它纳入 P0-B3，而不是留给后续视觉开发。

目标是：

- 配置文件成为实际门禁规则的唯一来源。
- 未知检查项、重复 ID、无效严重级别均导致明确错误。
- 必需门禁缺失时，验证失败，而不是默认通过。
- `PASS`、`FAIL`、`NOT_RUN` 在 CLI、报告和发布流程中保持一致。
- 每次验证记录实际使用的配置版本或哈希。

否则，文档说一个标准、代码执行另一个标准，整个质量体系就缺少可信的依据。

## 五、本地模型与云端 API：不要靠扩大上下文解决所有问题

本地模型当前可以承担受控、边界清晰的任务，但不能预设它一定能够独立完成整篇论文的高质量研究和课程设计。

建议采用混合路由，但必须由明确的策略控制。

| 任务                      | 推荐执行方式                | 原因             |
| ----------------------- | --------------------- | -------------- |
| PDF / HTML 解析、SourceMap | 本地确定性程序               | 不需要消耗模型推理能力    |
| 分节研究                    | 本地模型先试跑；复杂或失败任务可按策略升级 | 先测真实能力，再决定路由   |
| 论文要素映射、课程规划             | 规则约束 + 模型辅助           | 必须同时满足完整性与教学逻辑 |
| 公式推导、复杂实验解释             | 更强模型辅助，保留原文证据与人工核验    | 错误成本高          |
| 单元初稿                    | 本地模型处理有明确边界的任务        | 降低成本、保护数据      |
| JSON 验证、去重、引用校验、组装      | 本地确定性程序               | 不能依赖模型自我判断     |
| HTML 渲染、导航和浏览器测试        | 本地工程工具                | 属于可确定性验证的工程任务  |

### 路由必须有明确的失败语义

建议至少提供三个可配置模式：

- `local-only`：不向外部 API 发送内容，能力不足时明确失败或待处理。
- `hybrid`：按任务复杂度、隐私要求和质量结果选择模型。
- `cloud-preferred`：优先使用符合当前策略的外部模型，但仍遵循隐私与预算限制。

所有模式都应遵守以下规则：

1. 不允许静默切换模型。
2. 外部服务失败后，不允许自动降级并把低质量结果标记为成功。
3. 每次升级、降级或重试都必须写入运行记录。
4. 外部 API 必须受预算、超时和速率限制控制。
5. 涉及尚未授权外传的原始文献或内部材料时，不得擅自上传到云端。
6. 云端模型的可用地区、数据保留政策、价格和输出限制，应在接入时依据官方资料核实，而不是写死未经验证的假设。

此外，32K 上下文是整个请求的上下文预算，不是 32K 的自由输入空间。系统提示词、输入内容、历史消息、输出预留及模型本身的限制都会影响实际可用空间。

因此，P0-B3 应保留分块和单元生成，而不是试图把整门课程塞进一次大请求。`max_output_tokens`、`finish_reason`、usage、耗时和成本必须真正贯穿每个阶段。

## 六、建议的分阶段交付顺序

## 01

P0-B2.1：真实研究验收

下一步

运行本地模型研究流程，核对处理区块、关键主张、证据链、表格结果、错误类型与运行记录。

交付物： 一份真实研究验收报告，明确通过项、失败项及是否需要调整研究策略。

## 02

P0-B3-A：冻结课程主数据契约

明确 `CourseMaster`、`LearningUnit`、`UnitDraft` 的字段、引用、版本和审核状态；从覆盖矩阵反推课程结构。

交付物： Schema、示例数据、契约测试与一份完整课程规划。

## 03

P0-B3-B：实现单元队列与局部重试

单元独立生成、校验、重试和审批；接入模型输出限制、截断处理和完整运行追踪。

交付物： 可以只重跑失败单元、不会静默覆盖已批准内容的流水线。

## 04

P0-B3-C：统一派生产物与质量门禁

从审核后的主数据生成课程 HTML、阅读版和演讲稿；完成门禁配置统一、覆盖与重复检查。

交付物： 内容一致、证据可追踪、失败可定位的课程生产包。

## 05

P1：16:9 课程展示与交互

等课程内容和主数据契约稳定后，再实现固定比例幻灯片、键盘导航、目录、进度、全屏、打印与浏览器验收。

交付物： 可用于正式讲授的静态课程展示系统。

## 06

P2：视觉解释、动画与进一步优化

先完善静态示意图和数据图表。只有在动画确实能帮助解释机制时，再引入相应动画工具与运行环境。

交付物： 有教学价值、可维护且经过验证的视觉资产。

## 七、最终验收标准：什么才算真正完成

我建议把项目完成定义为四个层次，而不是只看测试数量。

工程完成： 数据契约稳定，研究窗口可追踪，局部重试有效，配置与实际执行一致，所有失败均有明确状态。

研究完成： 重要论文要素没有未解决的关键遗漏，关键事实能够回溯到原文，主张和证据的关联经过验证。

教学完成： 课程不是论文摘要的简单扩写。读者能理解问题、方法、推导、实验、结果、局限，以及各部分之间的因果关系。

产品完成： 一篇论文能够生产为一套完整课程包，各产物保持一致，内部证据链完整，公开内容不泄露内部数据，人工审批和发布边界明确。

这里还应保留一条法律与学术治理原则：引用和展示原论文图表时，记录来源、版权声明与使用依据；对外发布前根据具体许可和使用方式进行审查。来源可追踪并不自动意味着所有内容都可以自由再发布。

## 我的最终判断

P0-B2 的技术方向正确。现在最容易犯的错误，不是开发得不够快，而是把输入完整性、覆盖规划和工程测试通过，过早解释成课程质量已经得到保证。

下一步只聚焦三件事：

1. 用实际固定的本地模型跑完 `lces run --only research`，产出可人工核验的研究资产。
2. 根据真实错误决定单元粒度与研究路由，而不是预先假设模型一定能够完成。
3. 冻结 `CourseMaster` / `UnitDraft` 契约，再实施 P0-B3 的任务队列、局部重试和统一派生产物。

先把一篇论文做成内容完整、证据可靠、教学清晰、能够重复生产的课程，再扩展到更多论文、视觉效果和自动化发布。这才是 LCES 从一个生成工具走向真正的内容工程系统的关键一步。
